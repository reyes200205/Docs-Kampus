Hay dos tipos de pull request, y cada uno va en una dirección distinta:

| PR | Dirección | Para qué | Cómo se mergea |
| --- | --- | --- | --- |
| **De tarea** | `feature/T-XX-...` → `develop` | Integrar tu trabajo | **Create a merge commit** |
| **De publicación** | `develop` → `main` | Publicar una versión | **Create a merge commit** |

<Callout title="Los PR no se abren solos">
  Hacer `git push` solo sube tus commits. El pull request lo abres tú en GitHub. A veces GitHub muestra un aviso amarillo **Compare & pull request** justo después del push; si no aparece, usa las ligas de abajo.
</Callout>

## PR de tarea: tu rama → develop

1. Sube tu rama:

   ```bash
   git push -u origin feature/T-05-api-login
   ```

2. Abre la comparación en GitHub. Cambia el repositorio y el nombre de tu rama:

   ```
   https://github.com/reyes200205/Docs-Kampus/compare/develop...feature/T-05-api-login
   ```

   O desde el repositorio: **Pull requests → New pull request**.

3. Revisa los selectores de arriba: **base: `develop`** ← **compare: `tu rama`**.
4. Título con la [convención](/docs/development/commits), por ejemplo `feat: agrega login con correo institucional`. Al mergear se conservan **tus commits**, y cada uno será una línea del changelog: por eso todos deben seguir la convención (CI los revisa).
5. Llena la plantilla (abajo) y da **Create pull request**.
6. Espera los checks en verde y la aprobación de otro integrante.
7. Mergea con **Create a merge commit** y borra la rama.

## PR de publicación: develop → main

Se abre cuando el equipo decide publicar lo que ya está en `develop`.

1. Abre esta liga (ya trae las ramas en el orden correcto):

   ```
   https://github.com/reyes200205/Docs-Kampus/compare/main...develop
   ```

2. Verifica la dirección: **base: `main`** ← **compare: `develop`**. La flecha apunta hacia `main`, que es a donde llega el código.
3. Abajo debes ver los commits que se van a publicar y los archivos que cambian.
4. Título: `chore(release): publica vX.Y.Z` (no afecta la versión, solo la identifica). Da **Create pull request**.
5. Espera los checks. El bot comenta qué versión se publicará y su changelog; revísalo.
6. Abre la flechita **▾** del botón verde y elige **Create a merge commit**. No uses *Squash*: se perderían los commits y el changelog quedaría con una sola línea.
7. Revisa la pestaña **Releases** del repositorio: ahí aparece la versión nueva, y en unos minutos también en [/changelog](/changelog).

### Así se ven los checks del PR de publicación

![Checks del PR de develop a main: dos saltados y tres exitosos](/docs/pull-requests/checks.png)

*Publicar versión* y *Desplegar en Cloudflare* aparecen como **Skipped**: es normal. Solo corren cuando el PR ya se mergeó a `main`.

## Cómo saber si lo abriste bien

### Al revés: base develop ← compare main

![Comparación al revés: base develop, compare main](/docs/pull-requests/al-reves.png)

Si arriba dice **base: `develop`** y **compare: `main`**, estás llevando `main` hacia `develop`. No lo crees: da clic en las flechas ⇄ entre los selectores para invertirlos. Otra pista: aparece un commit **"Merge pull request #..."** con **0 files changed**.

### There isn't anything to compare

![GitHub dice que no hay nada que comparar entre main y develop](/docs/pull-requests/nada-que-comparar.png)

Con base `main` y compare `develop`, este mensaje significa que **`main` ya tiene todo lo de `develop`**: no hay nada pendiente de publicar. Probablemente ya se publicó; revisa **Releases** o la pestaña **Pull requests → Closed**. Primero hay que llevar cambios nuevos a `develop`.

## Plantilla del PR

| Apartado | Qué poner |
| --- | --- |
| Qué hace este PR | Descripción breve del cambio y por qué es necesario |
| Tarea relacionada | Tarea y requisito, p. ej. `T-05 · RF-02 · Closes #12` |
| Cómo probarlo | Pasos para que quien revisa pueda verificarlo |
| Definition of Done | La lista de abajo, marcada |
| Notas para quien revisa | Decisiones de diseño, dudas abiertas, deuda técnica |

## Revisión

- Al menos **otro integrante** revisa y aprueba el PR.
- CI debe pasar. En el backend: formato, migraciones y pruebas (ver [Integración continua](/docs/backend/installation#integración-continua)). En la documentación: la convención de commits.
- Cómo se calcula la versión: ver [Versiones y changelog](/docs/development/releases).

## Resolver conflictos

Hay conflicto cuando tu rama y `develop` cambiaron las mismas líneas. GitHub lo avisa en el PR con **This branch has conflicts that must be resolved** y no deja mergear.

1. Trae `develop` a tu rama. Usa `merge`, no `rebase`: así no se reescriben commits que ya están en el PR.

   ```bash
   git switch develop
   git pull
   git switch feature/T-05-api-login
   git merge develop
   ```

2. Git marca cada archivo en conflicto (`git status` los lista como *both modified*). En cada uno, busca los bloques:

   ```text
   <<<<<<< HEAD
   lo que tiene tu rama
   =======
   lo que llegó de develop
   >>>>>>> develop
   ```

   Deja el código correcto, que muchas veces es **una combinación de los dos**, y borra las marcas. Si el conflicto es en código de otra persona, pregúntale en Slack antes de elegir.

3. Casos frecuentes:

   | Archivo | Qué hacer |
   | --- | --- |
   | `composer.lock` o `pnpm-lock.yaml` | No se editan a mano: toma el de `develop` (`git checkout --theirs <archivo>`) y vuelve a correr `composer update <paquete>` o `pnpm install`. |
   | Migraciones | Nunca cambies una migración que ya está en `develop`; crea una nueva con fecha posterior. |
   | `routes/api.php`, `meta.json` o tablas de endpoints | Casi siempre se conservan las dos partes: cada rama agregó sus propias líneas. |

4. Comprueba que todo sigue funcionando y termina el merge:

   ```bash
   php artisan test && ./vendor/bin/pint --test   # backend; en la app y en la documentación, pnpm lint
   git add .
   git commit                                      # Git propone "Merge branch 'develop' into ..."
   git push
   ```

5. El PR se actualiza solo y CI vuelve a correr. Si cambió mucho, pide otra revisión.

Para tener menos conflictos: PR pequeños, una tarea por rama y traer `develop` a tu rama seguido, no solo al final.

## Definition of Done

Una tarea se considera terminada cuando:

1. El código fue revisado por otro integrante mediante PR.
2. Las pruebas del módulo pasan.
3. La funcionalidad se verificó manualmente.
4. La documentación quedó actualizada (en la API, cada endpoint nuevo o modificado).

Lista de la plantilla del backend:

- [ ] El código fue revisado por otro integrante del equipo.
- [ ] Las pruebas del módulo pasan (`php artisan test`).
- [ ] El formato de código pasa (`./vendor/bin/pint --test`).
- [ ] La funcionalidad se verificó manualmente.
- [ ] La documentación de la API quedó actualizada si cambiaron endpoints.
- [ ] No se subieron credenciales, archivos `.env` ni datos personales.
