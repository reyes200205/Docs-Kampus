---

## Formato

```
tipo: descripción breve en presente
```

- El tipo va en minúsculas; la descripción, en español.
- La descripción dice **qué hace** el commit, en presente: "agrega", "corrige", "extrae".

## Tipos

| Tipo | Cuándo usarlo |
| --- | --- |
| `feat` | Nueva funcionalidad |
| `fix` | Corrección de un error |
| `test` | Agregar o ajustar pruebas |
| `docs` | Documentación |
| `refactor` | Cambio interno que no altera el comportamiento |
| `perf` | Mejora de rendimiento |
| `revert` | Revierte un commit anterior |
| `chore` | Configuración y dependencias |
| `ci` | Workflows de GitHub Actions |
| `build` | Sistema de build |
| `style` | Formato, sin cambios de lógica |

Opcionalmente, un alcance entre paréntesis: `docs(api): documenta el login`. Un cambio que rompe compatibilidad lleva `!`: `feat!: cambia las rutas de la API`.

<Callout type="warn" title="Se revisa automáticamente">
  Un commit que no siga la convención se rechaza en CI en los tres repositorios, y también al hacer `git commit` en `docs-kampus` y en la app. El tipo decide la versión que se publica: ver [Versiones y changelog](/docs/development/releases).
</Callout>

## Ejemplos

```
feat: agrega endpoint de registro con validación de dominio
fix: corrige expiración del token de Sanctum
test: agrega pruebas del algoritmo de descubrimiento
docs: actualiza el contrato de la API
refactor: extrae la consulta de descubrimiento a un Builder
chore: configura el pipeline de CI
```
