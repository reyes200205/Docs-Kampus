El descubrimiento muestra perfiles de estudiantes de las instituciones participantes para que el alumno responda **Me interesa** o **Pasar** (RF-05). Los filtros por universidad, carrera e intereses se guardan en el perfil y se conservan entre sesiones (RF-06).

<Callout title="Estado">
  Llega con T-09 en el [PR #31](https://github.com/WilbertDevMx/backend-kampus/pull/31), que está en revisión. Esta página describe cómo queda la API al fusionarse. La generación del match (T-10) se agregará después a la respuesta de [`POST /api/swipes`](#evaluar-un-perfil).
</Callout>

Todas las rutas de esta página requieren un token de Sanctum, un correo verificado y una cuenta `student` (ver [Autenticación](/docs/backend/api/authentication)). **[Nuevo]** Una cuenta de staff (`moderator` o `admin`) recibe `403` en todas ellas, igual que en las rutas de perfil.

## Quién aparece

Un perfil sale en el descubrimiento solo si cumple todo esto:

- es de un **estudiante** con el correo verificado y sin suspensión. **[Nuevo]** Nunca aparecen moderadores ni administradores;
- tiene perfil creado;
- **no hay bloqueo** entre los dos, en ningún sentido (RF-13);
- quien busca **todavía no lo evalúa**. Un perfil al que ya se le dio Me interesa o Pasar no vuelve a salir.

Que otra persona ya haya evaluado a quien busca no cambia nada: su perfil sigue saliendo.

### Orden

1. Primero, los perfiles con **más intereses en común** con quien busca.
2. Si empatan, los de **su misma universidad**.
3. Al final, por antigüedad de la cuenta, para que el orden sea estable entre peticiones.

El orden se calcula en la API con un criterio intercambiable (patrón Strategy, ver [Patrones de diseño](/docs/project/unit-1/design-patterns)), así que se puede ajustar después de las pruebas de usabilidad sin cambiar la app.

## Obtener perfiles

```http
GET /api/discover?limit=10
Accept: application/json
Authorization: Bearer <token>
```

| Parámetro | Tipo | Por defecto | Descripción |
| --- | --- | --- | --- |
| `limit` | entero de 1 a 20 | `10` | Cuántos perfiles traer en la tanda. |

No hay paginación: como un perfil evaluado ya no regresa, para seguir basta con pedir otra tanda. Si `data` viene vacío, ya no hay más perfiles con esos filtros.

### Respuesta `200`

```json
{
  "data": [
    {
      "id": 12,
      "name": "Ana López",
      "university": {
        "id": 1,
        "name": "Universidad Tecnológica de Torreón",
        "short_name": "UTT"
      },
      "career": "Ingeniería en Tecnologías de la Información",
      "semester": 6,
      "age": 21,
      "bio": "Me gusta la fotografía y la música.",
      "shared_interests": 2,
      "interests": [
        { "id": 3, "name": "Fotografía", "category": "cultura" },
        { "id": 5, "name": "Música", "category": "entretenimiento" }
      ],
      "photos": [
        {
          "id": 40,
          "position": 1,
          "temporary_url": "https://<bucket>/profiles/12/5f1c...jpg?X-Amz-Expires=900&X-Amz-Signature=..."
        }
      ]
    }
  ],
  "filters": {
    "universities": [],
    "career": null,
    "interests": []
  }
}
```

| Campo | Descripción |
| --- | --- |
| `id` | Id del usuario. Es el que se manda en [`POST /api/swipes`](#evaluar-un-perfil). |
| `university` | Institución del perfil. |
| `age` | Edad calculada. La API **no** envía la fecha de nacimiento. |
| `shared_interests` | Cuántos intereses comparte con quien busca. Sirve para mostrar "2 intereses en común". |
| `photos` | Fotos en orden de `position`. Cada `temporary_url` es una URL firmada que **vence a los 15 minutos** (RNF-03); si vence, se pide la tanda otra vez. |
| `filters` | Los filtros con los que se armó la tanda. |

La tarjeta no trae correo, fecha de nacimiento ni zona: solo lo que se muestra en pantalla.

### Errores

| Código | Cuándo |
| --- | --- |
| `401` | Sin token o con un token vencido. |
| `403` | El correo no está verificado, o la cuenta es de staff (`Tu cuenta no tiene acceso a esta sección.`). |
| `422` | `limit` no es un entero de 1 a 20. |

## Filtros

Los filtros se guardan en el perfil (`profiles.discovery_filters`) y `GET /api/discover` los aplica solos. Una lista vacía o una carrera `null` significan **sin filtro**.

| Campo | Tipo | Reglas | Cómo filtra |
| --- | --- | --- | --- |
| `universities` | lista de ids | Hasta 10; universidades **activas** | El perfil es de alguna de esas universidades. Vacío: todas las participantes. |
| `career` | texto o `null` | Hasta 120 caracteres; se le quitan los espacios de los extremos | La carrera **contiene** ese texto, sin importar mayúsculas. `sistemas` encuentra "Ingeniería en Sistemas". |
| `interests` | lista de ids | Hasta 20; intereses del catálogo (`GET /api/interests`) | El perfil tiene **al menos uno** de esos intereses. |

### Leer los filtros

```http
GET /api/discover/filters
Accept: application/json
Authorization: Bearer <token>
```

Responde `200`. Si el alumno nunca guardó filtros, todos vienen vacíos:

```json
{
  "data": {
    "universities": [],
    "career": null,
    "interests": []
  }
}
```

### Guardar los filtros

```http
PUT /api/discover/filters
Accept: application/json
Authorization: Bearer <token>
Content-Type: application/json

{
  "universities": [1, 2],
  "career": "sistemas",
  "interests": [3, 5]
}
```

**Reemplaza** los filtros anteriores: un campo que no se envía queda sin filtro. Para quitar todos, se manda `{}`. Responde `200` con los filtros como quedaron guardados, en el mismo formato que la lectura.

Si algo no es válido, responde `422` con el error en el campo, por ejemplo `universities.0` cuando la universidad no existe o está inactiva, o `interests.1` cuando el interés no está en el catálogo.

`PATCH /api/profile` también acepta `discovery_filters`, con las mismas reglas, y guarda el mismo formato. Un campo que no esté en la tabla de arriba se rechaza.

## Evaluar un perfil

```http
POST /api/swipes
Accept: application/json
Authorization: Bearer <token>
Content-Type: application/json

{
  "user_id": 12,
  "liked": true
}
```

`liked: true` es **Me interesa** y `liked: false` es **Pasar**. Cada perfil se evalúa una sola vez.

### Respuesta `201`

```json
{
  "data": {
    "user_id": 12,
    "liked": true
  }
}
```

### Errores

| Código | Cuándo | Mensaje |
| --- | --- | --- |
| `422` | El perfil no existe, es de staff, hay un bloqueo entre los dos, está suspendido, no tiene perfil o es el propio usuario. Todos los casos dan **el mismo mensaje**, para no revelar cuál es. | `Este perfil no está disponible.` (en `errors.user_id`) |
| `422` | Falta `user_id` o `liked`, o `liked` no es booleano. | Error de validación en el campo |
| `409` | Ese perfil ya se evaluó. La primera respuesta es la que cuenta. | `Ya evaluaste este perfil.` |
| `403` | El correo no está verificado, o la cuenta es de staff. | |

Ejemplo de `422`:

```json
{
  "message": "Este perfil no está disponible.",
  "errors": {
    "user_id": ["Este perfil no está disponible."]
  }
}
```

## Flujo sugerido en la app

1. Al abrir Descubrir, pedir `GET /api/discover` y mostrar las tarjetas en orden.
2. En cada gesto, mandar `POST /api/swipes`. Un `409`, o el `422` de perfil no disponible, se tratan como evaluado: se quita la tarjeta y se sigue.
3. Cuando queden pocas tarjetas, pedir otra tanda. Las ya evaluadas no regresan.
4. En la pantalla de filtros, leer con `GET /api/discover/filters`, guardar con `PUT` y volver a pedir `GET /api/discover`.

## Rendimiento

El criterio de terminado de T-09 pide responder en menos de 500 ms. Con 2,000 estudiantes de prueba (5 intereses y 2 fotos cada uno) y 800 perfiles ya evaluados, `GET /api/discover` tardó entre 35 y 45 ms. Las consultas a la base suman unos 12 ms y no crecen con el tamaño de la tanda (sin consultas N+1).
