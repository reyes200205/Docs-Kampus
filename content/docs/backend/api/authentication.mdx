La API usa **Laravel Sanctum** con tokens personales (Bearer). La app obtiene un token al iniciar sesión y lo envía en cada petición protegida. Los tokens **expiran a los 7 días** (RNF-02).

## Iniciar sesión

```http
POST /api/login
Accept: application/json
Content-Type: application/json

{
  "email": "ana.lopez@utt.edu.mx",
  "password": "********",
  "device_name": "iphone-ana"
}
```

`device_name` es opcional y sirve para identificar la sesión (por defecto, `api`). El correo se compara sin importar mayúsculas ni espacios.

### Respuesta `201`

```json
{
  "token": "kampus_1|Xk3...",
  "token_type": "Bearer",
  "expires_at": "2026-10-22T18:00:00+00:00",
  "user": {
    "id": 1,
    "name": "Ana López",
    "email": "ana.lopez@utt.edu.mx",
    "email_verified_at": "2026-10-01T18:00:00+00:00",
    "role": "student",
    "university_id": 1
  }
}
```

**[Nuevo]** Los campos `role` y `university_id` se agregaron con T-40. Un administrador tiene `university_id` en `null`, porque ve todas las universidades.

### Errores

| Código | Cuándo | Mensaje |
| --- | --- | --- |
| `422` | Faltan campos, la contraseña es incorrecta o el correo no existe. Los dos últimos casos dan **el mismo mensaje**, para no revelar qué correos están registrados. | `Las credenciales no son correctas.` |
| `403` | El correo todavía no se verifica (RF-01). | `Verifica tu correo institucional antes de iniciar sesión.` |
| `403` | **[Nuevo]** La cuenta está suspendida por moderación o es de staff desactivado (RF-15, [T-41](/docs/backend/api/staff#desactivar-o-reactivar-una-cuenta)). Con la contraseña incorrecta se recibe el `422` de siempre, sin revelar la suspensión. | `Tu cuenta está suspendida.` |
| `429` | Hubo **5 intentos fallidos** con el mismo correo desde la misma IP. El bloqueo dura **15 minutos**, aunque luego se ponga la contraseña correcta. Un inicio de sesión correcto reinicia el contador. | `Demasiados intentos fallidos. Intenta de nuevo en 15 minutos.` |

Cada intento fallido y cada bloqueo se registran en `storage/logs/security.log`, con el correo enmascarado (`an****@utt.edu.mx`).

## Enviar el token

```http
GET /api/user
Accept: application/json
Authorization: Bearer <token>
```

### Respuesta `200`

Solo trae los campos públicos del usuario (`UserResource`):

```json
{
  "data": {
    "id": 1,
    "name": "Ana López",
    "email": "ana.lopez@utt.edu.mx",
    "email_verified_at": "2026-10-01T18:00:00+00:00",
    "role": "student",
    "university_id": 1
  }
}
```

### Respuesta `401`

Sin token, con un token inválido o con uno que ya expiró:

```json
{
  "message": "Unauthenticated."
}
```

Las rutas de usuario requieren `auth:sanctum` y `verified`. Además, la API limita a **120 peticiones por minuto** por usuario (`429` si se pasa).

## Cerrar sesión

```http
POST /api/logout
Accept: application/json
Authorization: Bearer <token>
```

Responde `204` sin contenido. Revoca **solo el token de esa petición**: las sesiones en otros dispositivos siguen activas.

## Roles

| Rol | Quién es | Qué ve en la app |
| --- | --- | --- |
| `student` | Alumno que se registra con su correo institucional. | Descubrir, Cerca, Chats, Grupos y Perfil. |
| `moderator` | Staff de **una sola** universidad. Lo crea un administrador. | Solo el panel de administración: usuarios, reportes y grupos de su universidad. |
| `admin` | Staff con acceso a todas las universidades. Lo crea otro administrador. | El panel completo, incluida la gestión de staff. |

Los permisos se validan en la API con *Policies*: si un moderador pide datos de otra universidad, la API responde `403`, aunque la app no muestre esa opción. El staff no puede usar las rutas sociales (swipe, match, chat). El primer administrador se crea en el servidor con `php artisan kampus:create-admin` (T-40).

## Registro

Solo se aceptan correos institucionales (RF-01). Los dominios aceptados salen de la tabla `universities` (columna `email_domains`, solo universidades activas); ya no existe la variable `KAMPUS_ALLOWED_EMAIL_DOMAINS`. Ver [El proyecto](/docs/project/kampus#instituciones). **[Nuevo]** El registro público siempre crea cuentas `student`: si la petición manda `role`, se ignora. Las cuentas de staff solo las crea un administrador (T-41).

### Crear la cuenta

```http
POST /api/register
Accept: application/json
Content-Type: application/json

{
  "name": "Ana López",
  "email": "ana.lopez@utt.edu.mx",
  "password": "********",
  "password_confirmation": "********"
}
```

| Campo | Reglas |
| --- | --- |
| `name` | Obligatorio, hasta 255 caracteres. |
| `email` | Obligatorio, correo válido de un dominio institucional y que no esté registrado. Se guarda sin espacios y en minúsculas, igual que en el login, así que `Ana.Lopez@UTT.edu.mx` cuenta como el mismo correo. |
| `password` | Obligatoria, con `password_confirmation` igual. Mínimo 8 caracteres, con mayúsculas, minúsculas y números (en producción también se rechazan contraseñas filtradas). |

La cuenta queda asignada a la universidad de su dominio. La API manda un correo con el enlace de verificación (por la cola de trabajos) y responde `201`:

```json
{
  "message": "Registro exitoso. Revisa tu correo para verificar tu cuenta.",
  "user": {
    "id": 1,
    "name": "Ana López",
    "email": "ana.lopez@utt.edu.mx",
    "email_verified_at": null,
    "role": "student",
    "university_id": 1
  }
}
```

La cuenta todavía **no puede iniciar sesión**: el login responde `403` hasta que se verifique el correo.

#### Errores

| Código | Cuándo |
| --- | --- |
| `422` | Falta un campo, el correo ya está registrado, la contraseña no cumple la política o el dominio no es de una universidad participante (`El dominio del correo no está permitido.`). |
| `429` | Más de **6 registros por minuto** desde la misma IP. |

### Verificar el correo

El enlace del correo apunta a la API y **vence a los 60 minutos**:

```http
GET /api/email/verify/{id}/{hash}?expires=...&signature=...
```

| Código | Cuándo | Mensaje |
| --- | --- | --- |
| `200` | El enlace es válido. También si la cuenta ya estaba verificada. | `Correo verificado correctamente.` |
| `403` | El enlace venció o se modificó (la firma no coincide). | |
| `403` | El `hash` no corresponde al correo de esa cuenta. | `El enlace de verificación no es válido.` |

Después de verificar, el usuario ya puede [iniciar sesión](#iniciar-sesión).

## Recuperar la contraseña

**[Nuevo]** Llega con T-45 en el [PR #34](https://github.com/WilbertDevMx/backend-kampus/pull/34), que está en revisión (rúbrica de la Unidad 3, criterio "Recuperación de Contraseñas").

El flujo tiene dos pasos:

1. En la pantalla "Olvidé mi contraseña", la app manda el correo a `POST /api/forgot-password`.
2. Llega un correo con un enlace que abre la pantalla `auth/reset-password` de la app, con `token` y `email` en la URL. Ahí la persona escribe su contraseña nueva y la app la manda a `POST /api/reset-password`.

### Pedir el enlace

```http
POST /api/forgot-password
Accept: application/json
Content-Type: application/json

{
  "email": "ana.lopez@utt.edu.mx"
}
```

Responde `200` **exista o no el correo**, para no revelar qué cuentas están registradas:

```json
{
  "message": "Si el correo está registrado, te enviamos un enlace para restablecer tu contraseña."
}
```

- El correo llega en español ("Restablece tu contraseña de Kampus") y sale por la cola de trabajos, igual que el de verificación.
- El enlace **vence a los 60 minutos** y **solo sirve una vez**. La API guarda un hash del token, nunca el token.
- Si se pide otro enlace para el mismo correo antes de 60 segundos, no se manda otro correo, aunque la respuesta sea la misma.
- La API permite **6 peticiones por minuto** desde la misma IP; después responde `429`. Un correo mal escrito da `422`.

El enlace apunta a `PASSWORD_RESET_URL`, que por defecto es `http://localhost:8081/auth/reset-password`:

```text
http://localhost:8081/auth/reset-password?token=3f9c...&email=ana.lopez%40utt.edu.mx
```

### Restablecer la contraseña

```http
POST /api/reset-password
Accept: application/json
Content-Type: application/json

{
  "token": "3f9c...",
  "email": "ana.lopez@utt.edu.mx",
  "password": "********",
  "password_confirmation": "********"
}
```

La contraseña nueva sigue la misma política que el registro: mínimo 8 caracteres, con mayúsculas, minúsculas y números. Si todo es válido, responde `200`:

```json
{
  "message": "Tu contraseña se restableció. Inicia sesión con la nueva."
}
```

Al restablecerla se **cierra la sesión en todos los dispositivos** (se revocan todos los tokens), así que si alguien más tenía acceso a la cuenta, lo pierde. Después, la persona [inicia sesión](#iniciar-sesión) con la contraseña nueva.

#### Errores

| Código | Cuándo | Mensaje |
| --- | --- | --- |
| `422` | El token es inválido, ya venció o ya se usó, o el correo no corresponde. Todos los casos dan **el mismo mensaje**. | `El enlace para restablecer la contraseña no es válido o ya venció.` (en `errors.email`) |
| `422` | La contraseña no cumple la política, la confirmación no coincide o falta un campo. | Error de validación en el campo |
| `429` | Más de 6 peticiones por minuto desde la misma IP. | |

Cada solicitud y cada cambio de contraseña quedan en `storage/logs/security.log`, con el correo enmascarado.
