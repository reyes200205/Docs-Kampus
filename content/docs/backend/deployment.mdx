El entorno de pruebas corre en **un solo servidor de AWS (EC2) con Docker Compose**. Toda la definición está en `compose.prod.yaml` del backend.

## Servicios

<Mermaid chart={`
flowchart LR
    Usuario((App)) -->|HTTPS 443| nginx
    nginx -->|/app WebSocket| reverb
    nginx -->|resto| app[app · PHP-FPM]
    app --> db[(PostgreSQL)]
    queue --> db
    queue -->|eventos| reverb
    app --> S3[(S3 privado)]
    queue -->|correos| Resend
    certbot -.->|certificado| nginx
`} />

| Servicio | Qué hace |
| --- | --- |
| `nginx` | Entrada pública con HTTPS. Manda `/app` al WebSocket y lo demás a PHP. |
| `certbot` | Renueva el certificado de Let's Encrypt; Nginx toma el nuevo cada 6 horas. |
| `app` | La API (PHP-FPM 8.3). |
| `queue` | La cola: correos de verificación y recuperación, y eventos como `match.created`. |
| `scheduler` | Las tareas programadas de Laravel. |
| `reverb` | El WebSocket ([Tiempo real](/docs/backend/api/chat/realtime)); solo se ve dentro de la red de Docker. |
| `db` | PostgreSQL 16, con los datos en el volumen `pgdata`. |

Las imágenes se guardan en **S3** (bucket privado, con URLs firmadas) y los correos salen por **Resend**.

## Antes de desplegar (una sola vez)

1. **Servidor:** una instancia EC2 con Ubuntu 24.04 y al menos 2 GB de RAM (`t3.small` o `t4g.small`), con IP elástica. En su grupo de seguridad solo se abren 22 (SSH), 80 y 443.
2. **Dominio:** un registro DNS `A` del dominio de la API a la IP elástica.
3. **S3:** un bucket **privado** ("Block all public access" activado) y un usuario de IAM con permiso solo sobre ese bucket (`s3:GetObject`, `s3:PutObject` y `s3:DeleteObject`). Nunca se usan las llaves de la cuenta.
4. **Resend:** el dominio verificado y una API key con permiso **solo de envío**. Sin dominio verificado, Resend solo entrega correos a la cuenta dueña y los alumnos no recibirían la verificación.

## Variables de producción

Se copian de `.env.production.example` a `.env.production`, que **nunca** se sube al repositorio. Las que cambian respecto a local:

| Variable | Valor |
| --- | --- |
| `API_DOMAIN` · `ACME_EMAIL` | Dominio de la API y correo para Let's Encrypt. |
| `APP_ENV` · `APP_DEBUG` | `production` · `false` |
| `APP_URL` | `https://<dominio-de-la-API>` |
| `FRONTEND_URLS` | Origen de la app web, para CORS. |
| `PASSWORD_RESET_URL` | Pantalla de la app que abre el enlace de recuperación (`/auth/reset-password`). |
| `TRUSTED_PROXIES` | `172.16.0.0/12`, la red de Docker, para leer la IP real detrás de Nginx. |
| `SANCTUM_TOKEN_EXPIRATION` | `10080` minutos (7 días). |
| `BROADCAST_CONNECTION` · `REVERB_*` | `reverb` y credenciales propias del entorno. |
| `REVERB_ALLOWED_ORIGINS` | **[Nuevo]** El dominio de la app web **y** el de la API, separados por coma. La app de celular manda como origen el dominio de la API; sin él, el chat en tiempo real no conecta en el celular. Ver [Tiempo real](/docs/backend/api/chat/realtime#variables-del-backend). |
| `PROFILE_PHOTOS_DISK` · `GROUP_IMAGES_DISK` · `AWS_*` | `s3` y las llaves del usuario de IAM. |
| `AWS_ROOT` | **[Nuevo]** Carpeta dentro del bucket, cuando dos entornos lo comparten (producción usa `produccion`). Vacía, los archivos van a la raíz. Se pone antes del primer archivo: si se cambia después, los anteriores quedan fuera de alcance. Llega con el [backend #81](https://github.com/WilbertDevMx/backend-kampus/pull/81). |
| `MAIL_*` | SMTP de Resend. |
| `LOG_LEVEL` · `LOG_SECURITY_DAYS` | `warning` · `90` días de `security.log`. |

## Desplegar

```bash
git clone https://github.com/WilbertDevMx/backend-kampus.git && cd backend-kampus
cp .env.production.example .env.production   # y llena los valores marcados con <...>
docker compose -f compose.prod.yaml --env-file .env.production run --rm app php artisan key:generate --show
docker compose -f compose.prod.yaml --env-file .env.production up -d --build db app
docker compose -f compose.prod.yaml --env-file .env.production exec app php artisan migrate --force
docker compose -f compose.prod.yaml --env-file .env.production exec app php artisan db:seed --class=CatalogSeeder --force
docker compose -f compose.prod.yaml --env-file .env.production exec app php artisan db:seed --class=ZoneSeeder --force
docker compose -f compose.prod.yaml --env-file .env.production up -d --build
docker compose -f compose.prod.yaml --env-file .env.production exec app php artisan kampus:create-admin
```

- La llave que imprime `key:generate --show` va en `APP_KEY` antes del `up`.
- La primera vez se levantan solo `db` y `app` para migrar: la cola y el scheduler fallan si arrancan antes de que existan las tablas.
- En producción **no** se corre `db:seed` sin `--class`: `DatabaseSeeder` crea un usuario de prueba.

<Callout title="En el servidor de Kampus">
  **[Nuevo]** Desde el 24 nov, en el EC2 de Kampus todos los comandos de esta página llevan además `-f compose.server.yaml` (después de `-f compose.prod.yaml`): `docker compose -f compose.prod.yaml -f compose.server.yaml --env-file .env.production ...`. Ese archivo solo existe en el servidor y hace que Nginx también atienda producción. Si se omite, Nginx se recrea sin él y producción deja de responder. Ver [Producción](#producción).
</Callout>

**[Nuevo]** El entorno de pruebas se actualiza solo: ver [Actualización automática](#actualización-automática). Para actualizar a mano: `git pull`, compilar `app` y luego `nginx` (por separado), `up -d` y `migrate --force`.

```bash
docker compose -f compose.prod.yaml --env-file .env.production build app
docker compose -f compose.prod.yaml --env-file .env.production build nginx
docker compose -f compose.prod.yaml --env-file .env.production up -d
docker compose -f compose.prod.yaml --env-file .env.production exec -T app php artisan migrate --force
docker compose -f compose.prod.yaml --env-file .env.production restart nginx
```

**[Nuevo]** `app`, `queue`, `scheduler` y `reverb` usan la misma imagen. Si se compilan juntos (`build` o `up -d --build` de todo), a veces fallan con `image "kampus-api:latest": already exists`; compilando `app` se deja lista la imagen de los cuatro. Ver [Errores resueltos](/docs/project/bug-log#image-already-exists-al-compilar-14-nov).

**[Nuevo]** Si cambias `.env.production`, recrea los contenedores que usan la API, porque la configuración se cachea al arrancar. Después reinicia Nginx: guarda la dirección interna de `app` de cuando arrancó, y si `app` se recrea responde `502` hasta reiniciarlo.

```bash
docker compose -f compose.prod.yaml --env-file .env.production up -d --force-recreate app queue scheduler reverb
docker compose -f compose.prod.yaml --env-file .env.production restart nginx
```

Lo mismo aplica después de un `up -d --build` que recree `app`: si `/up` responde `502`, reinicia Nginx.

## Actualización automática

**[Nuevo]** Desde el 17 nov, el entorno de pruebas se actualiza solo: **cada 5 minutos revisa `develop`** y, si hay commits nuevos, compila, migra y reinicia. Nadie tiene que entrar al servidor después de fusionar un PR; en unos 10 minutos ya está arriba.

| Pieza | Dónde | Qué hace |
| --- | --- | --- |
| `kampus-deploy.timer` | `/etc/systemd/system/` | Corre el servicio 5 minutos después de encender el servidor y luego cada 5 minutos. |
| `kampus-deploy.service` | `/etc/systemd/system/` | Corre el script una vez, con un tope de 20 minutos. Necesita Docker arriba. |
| `kampus-deploy` | `/usr/local/bin/` | El script que actualiza. |

### Qué hace en cada vuelta

1. Si ya hay una actualización en curso, no hace nada (un candado con `flock`).
2. Consulta `origin/develop`. Si el servidor ya está en ese commit, termina.
3. Si ese commit ya falló antes, no lo vuelve a intentar: espera al siguiente commit.
4. Avanza la copia del servidor con `git merge --ff-only`. Si no avanza en línea recta (alguien cambió algo a mano en el servidor), se detiene para revisarlo a mano.
5. Compila `app` y luego `nginx`, arma la configuración de Nginx con `kampus-nginx-conf` (**[Nuevo]**, desde el 24 nov; ver [Producción](#producción)), levanta todo con `up -d`, corre `migrate --force` y reinicia Nginx (para evitar el `502`).
6. Revisa `https://api-kampus.emulatornds.online/up` hasta 12 veces, cada 5 segundos.
7. Si responde `200`, borra las imágenes viejas de Docker y termina.

**Si algo falla** (la compilación, una migración o `/up`), anota ese commit como fallido, **regresa al commit anterior** y lo vuelve a desplegar. Así el servidor sigue con la última versión que funcionaba, y el commit con el error no se reintenta cada 5 minutos. Cuando se fusione el arreglo, el siguiente commit se despliega normal.

<Callout title="Ojo con las migraciones">
  Si una migración falla a la mitad, regresar el código no deshace lo que ya cambió en la base. Las migraciones se prueban en el PR (la CI corre las migraciones en una base limpia y luego las pruebas) para que esto no pase.
</Callout>

### Revisar qué pasó

```bash
journalctl -u kampus-deploy --since today      # lo que hizo hoy
journalctl -u kampus-deploy -n 50              # las últimas 50 líneas
systemctl list-timers kampus-deploy.timer      # cuándo toca la siguiente vuelta
sudo systemctl start kampus-deploy             # actualizar ahora, sin esperar
```

En el log se ve, por ejemplo, `Actualizando d5643fe -> 4172d8f` y `Listo: ...`. Si dice `Falló la actualización`, el commit fallido está en `/var/lib/kampus-deploy/fallido`.

Para pausarla (por ejemplo, mientras se revisa algo a mano): `sudo systemctl stop kampus-deploy.timer`, y `sudo systemctl start kampus-deploy.timer` para volver a activarla.

### Lo que no hace

- **No cambia `.env.production`.** Si un PR necesita una variable nueva, hay que agregarla en el servidor antes de fusionarlo, o el despliegue puede fallar y regresar a la versión anterior.
- **No corre seeders.** Si un PR agrega datos de catálogo, se siembran a mano.
- Solo sigue `develop`. **[Nuevo]** `main` lo despliega otro script, `kampus-deploy-prod`, en [Producción](#producción).

La app web de producción todavía no está definida: `FRONTEND_URLS` y `PASSWORD_RESET_URL` apuntan, por ahora, a `app.kodev.online`, igual que pruebas. Una web propia de producción necesita la llave pública de Reverb de producción.

### Un solo Nginx para los dos

Solo un contenedor puede tener los puertos 80 y 443, así que el **Nginx de pruebas atiende los dos dominios**. El stack de producción no levanta su propio `nginx` ni `certbot`.

<Mermaid chart={`
flowchart LR
    App((App)) -->|api-kampus...| nginx
    App -->|api.kodev.online| nginx
    nginx -->|red de pruebas| P[app y reverb de pruebas]
    nginx -->|red kampus-edge| R[app y reverb de producción]
    P --> PDB[(base de pruebas)]
    R --> RDB[(base de producción)]
`} />

- Nginx entra a una red de Docker compartida, `kampus-edge`. Ahí están `app` y `reverb` de producción, con los alias `kampus-prod-app` y `kampus-prod-reverb`.
- En `kampus-edge`, los nombres `app` y `reverb` son los de producción. Por eso, para pruebas, Nginx usa el nombre exacto de cada contenedor (`backend-kampus-app-1` y `backend-kampus-reverb-1`).
- Para producción, Nginx busca la dirección del contenedor en cada petición. Así, cuando la actualización recrea producción, no responde `502`.
- El certificado de `api.kodev.online` lo sacó el `certbot` de pruebas y vence el 22 feb 2027. El mismo `certbot` lo renueva junto con el de pruebas.

Estos archivos solo existen en el servidor (no están en el repositorio):

| Archivo | Qué hace |
| --- | --- |
| `~/backend-kampus/compose.server.yaml` | Mete el `nginx` de pruebas a `kampus-edge` y le monta `~/kampus-edge/conf.d` como su configuración, y el `public` de producción. |
| `~/kampus-prod/compose.server.yaml` | Le pone a producción su propia imagen, mete `app` y `reverb` a `kampus-edge` y apaga `nginx` y `certbot` en ese stack. |
| `~/kampus-edge/produccion.conf` | El bloque de Nginx de `api.kodev.online`. |
| `/usr/local/bin/kampus-nginx-conf` | Arma `~/kampus-edge/conf.d`: copia `produccion.conf` y genera `pruebas.conf` desde `docker/nginx/default.conf` del repo, con los nombres exactos de los contenedores. Si el archivo del repo cambia de forma que ya no puede hacerlo, se detiene y la actualización regresa a la versión anterior. |
| `kampus-deploy-prod` (`.service` y `.timer`) | Igual que la de pruebas, pero sobre `main` y `https://api.kodev.online/up`. Comparte el candado con `kampus-deploy`: nunca compilan las dos al mismo tiempo. |

### Comandos de producción

Desde `~/kampus-prod`, todo lleva `-p kampus-prod` y los dos archivos de Compose:

```bash
cd ~/kampus-prod
docker compose -p kampus-prod -f compose.prod.yaml -f compose.server.yaml --env-file .env.production ps
docker compose -p kampus-prod -f compose.prod.yaml -f compose.server.yaml --env-file .env.production logs -f app queue
journalctl -u kampus-deploy-prod --since today
```

- Si cambias el `.env.production` de producción, recrea `app queue scheduler reverb` de ese stack. No hace falta reiniciar Nginx.
- Si cambias `produccion.conf`, corre `sudo kampus-nginx-conf` y reinicia el `nginx` de pruebas.

## Datos de demostración

**[Nuevo]** Para la demostración, el entorno de pruebas puede cargar los estudiantes ficticios de `DemoSeeder` (T-34, [PR #46](https://github.com/WilbertDevMx/backend-kampus/pull/46), en la v0.2.0). Ver [qué crea](/docs/backend/installation#datos-de-demostración).

Como el servidor usa `APP_ENV=production`, el seeder se niega a correr salvo que `.env.production` tenga `DEMO_DATA_ENABLED=true`. Pon también una contraseña en `DEMO_PASSWORD` y vuelve a levantar `app`, porque la configuración se cachea al arrancar el contenedor:

```bash
docker compose -f compose.prod.yaml --env-file .env.production up -d app
docker compose -f compose.prod.yaml --env-file .env.production exec app php artisan db:seed --class=DemoSeeder --force
```

En una producción real, `DEMO_DATA_ENABLED` se queda en `false`.

## Certificado HTTPS (solo la primera vez)

Nginx arranca con un certificado autofirmado temporal. Con el DNS ya apuntando al servidor:

```bash
docker compose -f compose.prod.yaml --env-file .env.production run --rm --entrypoint sh certbot -c 'certbot certonly --webroot -w /var/www/certbot -d "$API_DOMAIN" --email "$ACME_EMAIL" --agree-tos --no-eff-email'
docker compose -f compose.prod.yaml --env-file .env.production exec nginx kampus-reload
```

Desde ahí `certbot` lo renueva solo. Si el primer comando falla, revisa que el DNS ya apunte a la IP elástica y que el puerto 80 esté abierto.

**[Nuevo]** Let's Encrypt ya no manda avisos de vencimiento por correo, así que `ACME_EMAIL` puede quedar vacío. En ese caso cambia `--email "$ACME_EMAIL"` por `--register-unsafely-without-email`. Así se sacó el certificado del entorno de pruebas.

## Monitoreo básico

- `https://<dominio-de-la-API>/up` responde `200` mientras la API está arriba. Se registra en un monitor externo gratuito para recibir un aviso si se cae. **[Nuevo]** En el entorno de pruebas es el monitor "Kampus API (/up)" de UptimeRobot: revisa cada 5 minutos, valida el certificado y avisa por correo a Wilbert. **[Nuevo]** Producción tiene el suyo, "Kampus API producción (/up)", con la misma configuración.
- Logs: `docker compose -f compose.prod.yaml logs -f app queue reverb`. Los de Laravel, incluido `security.log`, quedan en el volumen `logs`.
