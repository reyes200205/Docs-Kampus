## Pipelines por repositorio

### Backend (`backend-kampus`)

| Workflow | Cuándo corre | Pasos |
| --- | --- | --- |
| **CI** (`ci.yml`), check "Formato y pruebas" | Cada PR y cada push a `develop` y `main` | 1. Instala dependencias (con caché de `vendor/`). 2. `composer audit`. 3. `pint --test`. 4. `php artisan migrate --force` contra un servicio `postgres:16`. 5. `php artisan test`. |
| **Commits** (`commits.yml`) | Cada PR | commitlint revisa todos los commits del PR. |
| **Versión** (`release.yml`) | PR a `main` y push a `main` | En el PR comenta qué versión saldrá y su changelog; al fusionar crea el tag y el GitHub Release. |
| **Dependabot** | Semanal | Abre PR de actualización de dependencias, que pasan por el mismo CI. |

El check "Formato y pruebas" es **obligatorio** en la regla de `main` y `develop`: con una prueba en rojo, GitHub no deja fusionar.

### App (`Frontend-Kampus`)

| Workflow | Cuándo corre | Pasos |
| --- | --- | --- |
| **CI** (`ci.yml`), check "Tipos" | Cada PR y push | `pnpm install --frozen-lockfile` y `pnpm typecheck` (TypeScript) |
| **Commits** | Cada PR | commitlint |
| **Versión** | PR y push a `main` | Tag, release y changelog |

La app web se publica en Vercel (`app.kodev.online`), conectado al repositorio.

### Documentación (`Docs-Kampus`)

| Workflow | Cuándo corre | Pasos |
| --- | --- | --- |
| **Commits** | Cada PR | commitlint (y husky en la computadora de cada quien) |
| **Versión** | PR y push a `main` | Tag y release, `pnpm build` y publicación en Cloudflare Workers con `wrangler deploy` |

## Despliegue continuo del backend

Un *timer* de systemd revisa GitHub cada 5 minutos. Si la rama avanzó, el servidor compila la imagen, migra, levanta los contenedores y revisa `/up`. Si algo falla, **regresa solo al commit anterior** y no reintenta el commit roto. El detalle está en [Actualización automática](/docs/backend/deployment#actualización-automática).

| | Pruebas | Producción |
| --- | --- | --- |
| Rama | `develop` | `main` |
| Script | `kampus-deploy` | `kampus-deploy-prod` |
| Revisión de salud | `https://api-kampus.emulatornds.online/up` | `https://api.kodev.online/up` |
| Bitácora | `journalctl -u kampus-deploy` | `journalctl -u kampus-deploy-prod` |

Los dos comparten un candado: nunca compilan al mismo tiempo, porque el servidor tiene 2 GB de RAM.

Las corridas que no son exitosas ni fallidas son las que GitHub canceló porque llegó otro commit a la misma rama. **Las 9 fallas del CI del backend son el pipeline haciendo su trabajo:** cada una detuvo un PR que todavía no estaba listo (formato, una prueba o un aviso de seguridad en una dependencia) hasta que se corrigió. Por ejemplo, el 10 de noviembre `composer audit` detuvo todos los PR por un aviso de Symfony, que se arregló en el [backend #47](https://github.com/WilbertDevMx/backend-kampus/pull/47) ([Errores resueltos](/docs/project/bug-log)).
